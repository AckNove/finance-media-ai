# 高效开发执行协议 V1.0（本仓库落地版）

> 这一页把"怎么干活"写成可检查的规则。它不重复业务设计（那在 `docs/research_hub/`），
> 也不重复代码约定（那在 `AGENTS.md`）。**两者冲突时以 `AGENTS.md` 与当轮用户指令为准。**
>
> 原文见用户 2026-11-15 下发的《Harness 高效开发执行协议 V1.0》；这里是它在 finance-media-ai
> 里的具体落地：每条规则都写明在本仓库用哪个命令 / 哪个文件落实。

## 0. 目标

减少**无效**工作（重复分析、重复搜索、重复跑全量、无谓等待），不减少**有效**工作。
判断标准很朴素：这一轮结束时要能回答"用户能多做什么"，而不是"我跑了多少命令"。

## 1. 开工前（只做四件事）

```powershell
git rev-parse --abbrev-ref HEAD          # 分支
git log --oneline -3                     # 最近做了什么
git status --porcelain                   # 有没有未提交的东西（绝不覆盖用户改动）
git rev-list --left-right --count origin/main...HEAD   # 与远端差几笔
```

然后读**状态文件**，不要再从头扫仓库：

| 文件 | 它回答什么 |
| --- | --- |
| `PROJECT_STATE.md` | 项目现在多大、什么状态、数字是多少（每条都可由命令复算） |
| `TASK_BACKLOG.md` | 还欠什么，按 P0–P3 排 |
| `DECISION_LOG.md` | 为什么是现在这个做法（含否决过的方案） |
| `KNOWN_ISSUES.md` | 已知问题、证据、是否阻断 |

**状态文件与代码不一致时，以代码为准，并当场改状态文件**——不允许"文档说 A、代码是 B"过夜。

## 2. 范围控制

- 任务分 **P0**（影响核心链路能不能跑）/ **P1**（明显影响质量）/ **P2**（体验）/ **P3**（远期或已被用户推迟）。
- 一轮只围绕**一个业务交付目标**，交付物必须能在页面上或命令里看到。
- 中途发现的无关问题**写进 `TASK_BACKLOG.md`**，不在本轮顺手改（除非它阻断本轮）。
- 遇到阻塞（缺密钥、缺授权、缺素材）：**先做完所有不依赖它的工作**，再把阻塞项集中报告。

## 3. 执行

- 先找已有实现：`grep` 一个关键字比新写一个模块便宜得多。本仓库尤其如此——
  很多能力已经存在（`draft_gate`、`content_chain`、`task_timing`、`matrix_lint`…），重复造轮子是最贵的浪费。
- 同一份信息**只读一次**：读完就记进结论，不要为了"确认一下"再读一遍整个文件。
- 并行有前提：**两个并行任务不得修改同一个文件**；最终由一个负责人统一整合。

## 4. 测试策略（三级，不搞一刀切）

| 级别 | 什么时候跑 | 命令 |
| --- | --- | --- |
| 一级 | 改完立刻跑受影响模块 | `pytest tests/test_<模块>.py tests/test_<相关>.py -o addopts="" -q` |
| 二级 | 一个模块完成，跑相关集成 | `pytest tests/ -k "<关键词>" -o addopts="" -q` |
| 三级 | 本轮交付要做到能交付时 | `pytest -o addopts="" -q`（当前约 8 分钟，1524 例） |

- **不许为了变绿去删测试、跳过测试、放宽断言**。测试红了先怀疑实现。
- Mock 只能用于隔离外部（模型、网络、时钟）；**不许用 Mock 冒充"真实业务跑通了"**。
- 真实链路验收必须留证据：请求返回码、库里行数、文件大小与哈希、抽帧截图。

## 5. 计时（每轮必记）

一轮结束时记五段：`分析 / 开发 / 测试 / 外部等待 / 返工`，并写一句"主要耗时原因"。
某一段明显超预期时**换策略**，不要把同样的命令再跑一遍。

## 6. 停止条件（全部满足才收工）

1. 本轮交付目标完成且能看到；
2. 受影响测试通过（三级测试按 §4 判定该跑哪一级）；
3. 需要的真实链路验收通过（没有的话要说清"为什么这一轮不需要"）；
4. 没有未披露的关键问题；
5. `PROJECT_STATE.md` / `TASK_BACKLOG.md` / `DECISION_LOG.md` / `KNOWN_ISSUES.md` 已按实际结果更新；
6. 交付报告按 §8 写全；
7. 已提交并推送（`AGENTS.md` §1）。

## 7. 状态怎么更新（不许照抄上一轮）

```powershell
python -m backend.scripts.state_measure --md   # 现算一遍数字，贴进 PROJECT_STATE.md
python -m backend.scripts.matrix_lint          # 需求矩阵自查：DONE 行引用的文件必须真在
```

数字只能来自这两条命令和真实测试输出。**上一轮报告里的数字不算证据。**

## 8. 交付报告格式（九段，缺一不可）

1. 本轮目标
2. 实际完成事项
3. 修改文件及其用途
4. 测试与真实业务验收证据（含命令与输出）
5. 未完成事项及原因
6. 总耗时与各阶段耗时
7. 相比上轮减少了哪些重复工作
8. Git 提交与推送状态
9. 下一轮建议

## 9. 安全红线（效率优化不得触碰）

- `data/finance_media.db` **只读**：不迁移、不开 WAL、不 seed、不回填。
- 模型：**价目未知不发请求**；不自动充值；不把密钥写进日志/Git/报告。
- 素材：授权不明一律不进片；不伪造来源、不伪造"真实素材"。
- 发布：**永不自动发布**；`published` 必须有链接。
- Git：不 `reset --hard`、不 `clean -fd`、不 force push、不改历史、不覆盖用户未提交修改。
