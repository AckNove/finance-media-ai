## A. 工程缺陷 / 工程债

### A-01 真实视频独立来源只有 1 个

- **现状**：`S03A`（0–6 s）与 `S03B`（12–17 s）来自**同一个** NASA 文件
  `nasa_earth_rotation.mp4`，只是两个入点。任务 6 的「≥2 个真实视频片段」记为**部分完成**。
- **影响**：两个视频镜头观感相近（同一素材的不同时间窗），叙事上不算两个独立来源。
- **为什么没在 Phase 2 解决**：合法可商用的公开视频素材在授权范围内找不到第二个来源，
  而任务书明确禁止伪造来源、也明确说「不要求强行补充第二个独立来源」。
- **建议**：Phase 3 或之后引入第二个有明确授权的来源（政府/机构公开影像优先）。

### A-02 `qc/review/_sheet/` 空目录残留

- **现状**：`--stage review` 拼完联系表后删除临时目录，实测 `qc/review/_sheet/` 仍存在（0 个文件）。
- **影响**：无功能影响（Git 不跟踪空目录），属清理不彻底。
- **修法**：`stage_review()` 末尾改 `shutil.rmtree(..., ignore_errors=True)` 之后再判空。

### A-03 视觉复核材料（PNG）不在版本库里

- **现状**：`.gitignore` 第 66 行全局忽略 `*.png`，因此 `qc/review/` 的 18 帧与
  `contact_sheet.png`（约 19 MB）、`qc/frames/` 的 7 张关键帧都不入库。
- **影响**：换台机器或审阅者在 GitHub 上看不到这些图，必须本地重跑 `--stage review`。
- **为什么没改**：本轮是冻结轮，且这些图可再生；把它们塞进仓库会违背「大体积可再生资产不入库」。
- **建议**：若需要「看图就能验收」，可单独建一个 release 附件或外部图床，而不是塞进 Git 历史。

### A-04 引擎工作区磁盘占用约 3.8 GB

- **现状**：`content/jobs/phase2_media_engine_demo/project/c322cb9a56d9/.openkatana/` 存了画板帧
  序列与导入帧序列，实测该 job 目录总计 3,956 MB（M2.0 之后的 git 同步轮已确认）。
- **影响**：磁盘压力；但**帧缓存正是二次渲染只要 5 分钟**的原因。
- **建议**：加 `--stage clean`（保留画板、删中间帧），或在磁盘紧张时手工清理 `.openkatana/jobs/`。

### A-05 单帧 clip 必须靠镜头的 `loop` 字段撑满时长

- **现状**：`import_media` 对静态图片返回 `n=1` 的单帧 clip；时间轴的 `clips` 项**不接受** `loop`
  （`ContractError: clips.S01: unsupported fields: loop`），`loop` 是**镜头**字段。
- **影响**：已在 `backend/app/media/timeline.py` 里自动对 `n<=1` 的 clip 写 `entry["loop"]="loop"`，
  当前工作正常；但这是容易踩的契约陷阱（本轮踩过一次）。
- **建议**：保持现状 + 注释；若 OpenKatana 升级改了这条契约，需要回归。

### A-06 引擎时间轴历史快照会污染工作区

- **现状**：每次保存时间轴，引擎在 `project/c322cb9a56d9/` 下留一个 `timeline-<32位hash>.json`。
- **影响**：工作区出现未跟踪文件（本轮 2 个）。已在 `.gitignore` 加入忽略规则，不再污染。
- **状态**：**规则已加，属于处理过的卫生问题；保留在此是因为它每轮都会再出现**。

### A-07 渲染轮询无退避

- **现状**：`raw/_work/engine_calls.jsonl` 里 277 次调用中 `get_render` 占 215 次（约 19 分钟渲染期轮询）。
- **影响**：只是日志噪声与无用 CLI 进程，不影响结果。
- **建议**：轮询间隔改为指数退避（2s → 5s → 10s）。

### A-08 结尾卡附近两帧内容完全相同

- **现状**：`qc/review/16_anim_sh07.png` 与 `17_99_credits.png` 字节数相同（391,696 B）——
  因为两者都落在静态的结尾卡内（42.0 s 与 41.8 s）。
- **影响**：索引里有一帧冗余，不影响成片。
- **建议**：抽帧计划对静态结尾段只取一帧。

## B. 发布前法律与授权审核（代码无法解决）

> 这四条**必须在公开发布前由人工或法务确认**。本轮没有联网核实，所以一律标「待核实」，
> 不作任何未经证实的授权结论。

### B-01 NASA SVS 页面级授权条款与署名格式

- **待核实**：`svs.gsfc.nasa.gov` 上三张素材各自页面的当页使用条款、是否要求逐条引用其推荐署名格式、
  是否对再剪辑/配乐叠加有额外要求。
- **已确认的部分**（可作为下限）：NASA 媒体使用政策页
  `https://www.nasa.gov/nasa-brand-center/images-and-media/`；示例包内注明
  "NASA does not endorse OpenKatana"、"Media is not licensed as CC0"。
- **当前做法**：画面内逐条署名 + 一行 NASA 免责声明（未审查/未背书/第三方内容可能另有版权限制）。

### B-02 画面内第三方材料的授权核实

- **待核实**：阿波罗17号原片、蓝色弹珠、VIIRS 自转视频的画面里，是否含有第三方提供的图像、
  数据图层或商标，其授权是否独立于 NASA 主体政策。
- **影响面**：这是最容易被忽略的一条——NASA 自身素材为公共领域，不自动等于「画面里的每一层像素都可商用」。

### B-03 NOAA / JPSS 数据使用条款

- **待核实**：VIIRS / 蓝色弹珠的数据来源于 NOAA/JPSS，其数据使用条款与 NASA SVS 的再分发条款是否需要
  分别标注、是否要求「数据来源：NOAA」字样。
- **当前做法**：署名只写了 NASA SVS 与作者；**未单独标注 NOAA**。

### B-04 发布平台对免责声明的格式要求

- **待核实**：目标平台（抖音/视频号/YouTube 等）是否要求把「NASA 不背书」以更显眼的方式呈现，
  或要求把素材清单放到简介而不是画面内。

### B-05 字体 SIL OFL 1.1 的再分发条件

- **待核实**：把 Noto Sans SC 渲染进视频（而非随软件分发字体文件）是否需要在发布物中附带 OFL 文本。
- **当前做法**：画面内已写 `字体 Noto Sans SC · SIL OFL 1.1`，视为满足署名；许可证全文未随片分发。

## C. 视觉与音频待人工决策（程序无权代判）

### C-01 两个镜头入镜前约 0.5 秒画面偏空

- **现象**：`qc/review/10_trans_sh04.png`（15.65 s）与 `11_trans_sh05.png`（22.65 s）里只有小标题与
  坐标轴标签，标题与主体尚未淡入；两帧的 `signalstats` YAVG ≈ 32，**高于黑场阈值，QC 判为正常**。
- **原因**：画板 reveal 序列（kicker → 标题 → 主体）+ 0.4 秒转场叠加，视觉上像「空了一下」。
- **为什么不自动改**：这是节奏取舍，不是技术错误；改动会牵动全部画板的动画曲线。
- **可选修法**：把标题与首根柱子的 reveal 起点从当前帧位提前到第 0–2 帧。

### C-02 明亮背景下白色字幕对比度偏弱

- **现象**：`sh02`（NASA 自转视频，云层很亮）底部白字幕在亮区可读性下降。
- **现状**：字幕有描边，但描边宽度固定，未按背景亮度自适应。
- **可选修法**：给字幕加半透明底条，或按镜头亮度调描边/阴影。

### C-03 片尾信息密度较高

- **现象**：结尾卡同时承载标题、五条署名、NASA 免责行、统计行与结论句，共约 8 行。
- **现状**：已折行未裁切，但 2.5 秒内要读完偏紧。
- **可选修法**：拆成两张卡（署名卡 + 结论卡），或延长到 3.5 秒。

### C-04 响度未归一（−22.27 LUFS）

- **现状**：集成响度 −22.27 LUFS，比常见流媒体目标（−14 LUFS）低约 8 LU；真峰值 −6.27 dBTP。
- **为什么没做**：任务书明确禁止未经批准改变音频标准，本轮只做客观说明。
- **需要决策**：是否用 `loudnorm` 归一到 −14 LUFS（会改变峰值与动态，需要重渲音频并重跑 QC）。

### C-05 没有真人配音

- **现状**：`narration` 列 7 条文本完整保留（见分镜），但**没有任何音轨朗读它们**；
  字幕已明确只来自 `subtitle` 列，不存在「把字幕当配音」。
- **为什么没做**：本轮禁止调用付费 TTS、也禁止安装大型模型。
- **需要决策**：走真人录音，还是本地开源 TTS，还是保持无配音（当前版本是「视觉+音效+字幕」的默片式表达）。

### C-06 音效音量是否合适

- **现状**：六个音效相对配乐的分窗电平差为 +1.2 ~ +5.8 dB，全部「可闻且不刺耳」。
- **说明**：这只是**可闻性**的客观测量，不证明风格合适。`impact_soft`（+1.2 dB）是最保守的一个，
  有人可能觉得太弱。

### C-07 峰值余量

- **现状**：峰值 −6.3 dBFS。`whoosh_low` 与 `whoosh_tail` 是宽频噪声，峰值比其余音效高。
- **需要决策**：若后续做 loudnorm 归一，这两个音效会先撞到限幅器，可能需要在归一前单独压一点。
